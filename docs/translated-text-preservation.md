# 翻译后文字消失、仅剩 emoji：保护性修复

## 事实与待确认项

用户反馈部分场景翻译后文字消失，正文和回复预览的具体触发位置尚未确定；尚无消息样例或设备日志。

源码中确认了两个有条件的丢字路径（不能据此断言就是用户设备上的根因）：

1. **共享文本节点被空片段覆盖**：旧 `ContentNodes.replaceText` 使用 `IdentityHashMap` 保存译片。输入若是 `[text, emoji, text]` 且两处 `text` 为同一实例，单行译文分成 `[译文, 空串]` 后，空串覆盖译文，两处文字都变空，emoji 则保留。
2. **部分重建被误判为成功**：原实现的 `changed` 在子节点构造后即置为 true，父容器 `copy` 失败只恢复父容器。若首文本位于无法复制的容器内，译文被丢弃，而后面的文字仍被清空。首文本原本为空时，就可能只剩 emoji。

本地 Discord smali 的只读检查未发现 TextContentNode 渲染或 emoji 尺寸逻辑会主动清除前文；也未证实实际输入存在共享文本实例。折叠截断、Spoiler 隐藏、不同内容版本共用状态及服务端译文内容等仍需真实样例确认。本次不修改宿主 smali、Hook 时序或翻译请求协议。

## 最小修复

- `ContentNodes.java`：按节点出现位置分配译片，不再按对象身份覆盖；拒绝空译文；任一文本构造或容器复制失败就放弃整个替换结果。
- `StructurableTextFactory.java`：富文本无法完整重建时返回 null，调用方保留原始对象（包括文字、emoji、提及、代码）。不再降级到会丢失这些结构的纯文本。
- 保留既有按换行分配译片的策略，不新增依赖、不重构调度或缓存。
- 失败诊断仅记录节点计数和既有反射错误类型，不新增消息正文或 API 密钥日志。

### 影响和限制

正常成功路径仍保留 Markdown 与结构化节点；原本是纯文本的消息照常替换。无法重建的富文本会显示原文而不是部分译文。此时后台状态仍可能是翻译成功，图标不代表节点替换一定成功；本次不调整状态模型。

本修复不保证译片仍与原有样式/表情位置精确对齐，也不解决所有折叠、Spoiler 或接口返回异常内容的情况。

## 验证

新增 `ContentNodesTest` 与 `StructurableTextFactoryTest` 覆盖共享文本/容器实例、不同译片、首容器失败、后容器失败、父容器失败、文本构造失败、空译文、富文本构造不可用、emoji-only 不被无关译文覆盖，以及正常富文本/纯文本路径。

构建与单元测试：**该操作需要通过 GitHub Actions 执行。** 本地不运行 Gradle、javac 或测试。CI 结果以对应 PR / Actions 记录为准；这里不预先宣称测试通过。

### 设备复核（待用户执行）

1. 安装本分支 GitHub Actions 产出的 APK，并按当前 LSPosed 环境使 Discord 加载更新后的模块。
2. 在此前出问题的消息上切换原文/译文，确认两侧文字存在、emoji 保留。
3. 检查该消息的回复预览，以及滚动回看、重新进入频道后的显示。
4. 若含折叠内容或 Spoiler，分别展开/揭示后检查。不要据 CI 单测推断这些宿主 UI 场景已通过。
5. 若仍丢字，提供不含隐私的同格式样例、Discord/模块版本、切回原文是否恢复、展开后是否恢复。可提供 `node replacement aborted` / `markdown replacement unavailable` 附近的脱敏日志；不要提供 API 密钥或私聊正文。
